A USB-connected iPhone can be opened from the dashboard, mirrored and tapped (#152). The iOS agent lists the iPhones and iPads `devicectl` reports as plugged in over USB, trusted and in Developer Mode, by hardware UDID and with `kind: 'physical'`; only an iPhone has been tried on hardware, so an iPad is listed and nothing more is claimed for it.

The 30 s re-read of the device list (#1101) lists phones exactly as the register does, so a phone plugged in while the agent runs appears without a restart, and one unplugged leaves once nobody holds it; its capture helper, input channel and UI-test runner stop with it. A re-read gives `devicectl` 3 s and, when it fails or times out, offers the phones the last list had rather than none.

Opening one skips every simulator step and streams its screen through `device-capture-helper.app`, an ad-hoc signed app built on the agent Mac from the shipped Swift source (into `~/Library/Caches/tapflow`, off the event loop) and launched with `open` so it can hold the macOS Camera grant a screen-capture device needs. The helper opens its loopback connection with a per-launch nonce, and a failure it reports carries its reason. A capture failure the agent will not retry (Camera denied, two attached iPhones with the same name, which it refuses rather than guess between), or one that keeps failing, is sent to the session as an uncorrelated `device:boot-error`, which the dashboard shows. Taps, drags, long presses, typing, Return/Delete/Tab and the home and volume buttons go through the XCUITest runner, which gains `/tap`, `/drag`, `/type` and `/key` routes, builds for the device signed by `TAPFLOW_IOS_TEAM_ID` (optionally under `TAPFLOW_IOS_BUNDLE_PREFIX`), binds every interface with a per-launch token on every route, bounds what an unauthenticated connection can send and how long it may take, and is reached over the device's CoreDevice tunnel. The runner build is redone for a phone it was not built for. A drag is played after the finger lifts, as a straight line. A key or text the runner refuses (nothing focused) is answered as a failure, and typing looks for the focused field in whichever app is in front. Taps were tried on hardware; drags, typing and the volume buttons were not. Pinches, holding a button, the side button and ⌘/⌃/⌥ shortcuts are refused with `unsupported`, and input refused because the runner did not start says why it did not.

The first device build runs `xcodebuild -allowProvisioningUpdates`, which registers the phone in the team's Apple developer account and creates the App IDs `<prefix>.treerunner.host` and `<prefix>.treerunner.uitests` (prefix `dev.tapflow` unless `TAPFLOW_IOS_BUNDLE_PREFIX` is set) and a development provisioning profile for them.

`app:install` on a phone installs a device-signed build with `devicectl`: an `.ipa` (as Firebase App Distribution or an ad-hoc or development export produce) or a zip or tar of an iphoneos `.app`, over the installed copy, so a refused install leaves that copy and its data in place; only when the installed copy is signed for another App ID or team is it removed and the install tried once more. A simulator build cannot run on a phone, so when the app is already installed there (from TestFlight or Firebase) that copy is used and `app:install-done` carries a new optional `warning` saying so, with the installed version, which the dashboard shows and the relay repeats when it answers an install itself; otherwise the install fails asking for a device build. `app:launch` launches the installed app with `devicectl`, with launch arguments and environment. Neither has been tried on hardware yet.

Refused on a phone through each message's existing error reply: Full reset and run resets, clearing app data, the clipboard, network control, opening a URL and screenshots. `input:rotate` and `input:keyboard:toggle` have no reply, so a phone only logs them; the dashboard does not offer either for a phone. The relay never refuses a phone's session for the Mac's memory or CPU, since it boots nothing there, and `MacAdmission` says so. The dashboard counts USB devices on the Mac card, marks them with a USB badge and Connected in the device picker, opens an overloaded Mac's card when it has a phone, and leaves out the controls a phone cannot use.
