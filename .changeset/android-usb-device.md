A USB-connected Android phone can be offered beside the emulators (#152), **only with `TAPFLOW_ANDROID_USB_DEVICES=1` on the agent**; off by default, the listing is what it was before: emulators only, and no shell on any other device. With it on, every row of `adb devices` in state `device` that is not an emulator or a network serial is listed as `usb:<serial>`, reported as a physical device, named from `ro.product.marketname`, the phone's device name, or `ro.product.model`, its properties read with a 10 s bound so a phone that does not answer is left out rather than holding up the listing. A phone adb cannot drive — unauthorized, offline, in recovery — is named in the agent's output once per state it reaches, with no restart asked of it. Emulators are reported as emulators. A phone is reached by the serial in its `usb:` id whenever the serial map has dropped it — a listing that ran during a cable blip — so its stream restart, installs, rotation and clean-up still find it. Phones are part of the 30 s device list re-read exactly as of the register, so a phone plugged in or unplugged while the agent runs is offered or withdrawn without a restart. One that leaves the list has its session state retired as a reconnect retires it — its scrcpy session stopped, tapflow's claim on it and its install record forgotten — as they are when the relay connection is lost, and a rotation lock it still owes is kept; plugged back in, it is described afresh and the lock is written back by that listing, the re-read included. A phone's boot starts scrcpy and input only — no launch, wipe, gRPC, Lean mode or network reset — and always on scrcpy: `TAPFLOW_ANDROID_BACKEND=grpc` now applies to emulators only, where it used to send a non-emulator serial to the first emulator's gRPC port. Its shutdown stops only the stream and, on a normal shutdown, removes the scrcpy server and every tree dump jar (`tapflow-uidump-*.jar`, an earlier agent's included) tapflow pushed to `/data/local/tmp`. Full reset, network control, the clipboard and postures are refused on a phone through each message's error reply, which says why. On a phone, `app:install` no longer runs `pm clear` on the build's package first — the package comes from the build record, so it could name an app of the phone's owner — and `install -r` keeps the app's data; `app:clear-state` and a run reset's app-data step clear only a package tapflow installed in the session, and report any other as failed. Storage is never reclaimed on a phone, and an install there fails after 120 s plus 1 s per MB of the APK (`TAPFLOW_ANDROID_USB_INSTALL_TIMEOUT_MS` overrides it with whole milliseconds up to 2147483647, `0` for none; any other value keeps the default), with a message naming both a prompt on the phone and a slow install. The rotation lock a phone had at boot is written back at shutdown, synchronously on the agent's exit, or by the next listing that sees it, in this agent or the next (#1033). A rotate writes a lock on a phone only while its session is booted and once the lock from before is remembered — read then if the boot's read failed, and refused if that read fails too — and the boot's read and write and the write-back kill their `adb` child at 10 s, so a phone whose shell hangs does not gather one per re-read. On the agent's exit each scrcpy port forward is removed synchronously rather than left in the adb server. The lock is kept as follows: the agent goes by its own map and keeps a copy in `tapflow-usb-rotation.json` beside adb's keys, replaced whole through a temporary file. The scrcpy server is pushed as `tapflow-scrcpy-server.jar`, and a stream restart kills only its own server by `scid` (by that jar's path when no session names one), so a scrcpy a developer runs on the same phone is left alone. This applies to every device on the scrcpy path, emulators included: an emulator streaming without gRPC gets the renamed jar too, and its restart no longer kills every `scrcpy-server` on it.

The relay never hands a USB phone (`kind: 'physical'`) to a `device:lease`, which names only a platform: a client uses a phone only by naming it — the CLI's `--device <name>` or `--session <id>`, or an MCP client's `connect_device`. A lease refused because only phones are left says so.

`tapflow flow run` with neither `--device` nor `--session` no longer counts a USB phone (`kind: 'physical'`) among the booted devices it picks from: a phone always reads as booted, so a run could land on one nobody named, or stop with "multiple booted devices" because one is plugged in somewhere on the relay. With only phones booted it stops with an environment error that names them and says they are used only when named.
